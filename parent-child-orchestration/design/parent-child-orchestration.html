Claims Orchestration on Temporal

Parent–Child Orchestration: a claim workflow with a child workflow per track

1. Summary

One parent workflow per claim, ClaimLifecycleWorkflow (Java), owns the claim's stage. Each visit to a track is a child workflow on that track's own task queue and worker: TriageWorkflow and InvestigationWorkflow (Python), StpWorkflow (Java). Each payment is a PaymentWorkflow, a child of STP that finishes even if STP is stopped. Change events go to the parent, which forwards them to the active child. Human decisions are validated Updates on the workflow that waits for them. Workflows carry IDs; ClaimsPro holds claim data; the projection table holds business history; both histories reach S3 before Temporal's retention deletes anything.

2. Why parent–child

Temporal uses child workflows when a unit of work has its own worker fleet, its own owner or its own lifecycle. Each child here has at least one of these.

UnitWhy it is a workflow of its own
Triage, investigationAI workers; owned and released by the AI team
STPCore workers; owned and released by the core team
PaymentIts own audit trail; must finish even if STP is stopped
Claim (parent)The only place that changes the stage; holds routing and cross-track rules

Dispatch and appraisal have no separate owner or lifecycle, so they are activities inside STP.

One Temporal Cloud namespace per environment. Workers and the event bridge connect outbound only (gRPC with mTLS through PrivateLink). On-premises systems are reached over Direct Connect; inbound calls enter EKS through Kong. ClaimsPro calls run as their own deployment of the STP worker image, sized to ClaimsPro's limit. One EKS deployment per queue replaces today's single worker on EC2.

A new child per visit keeps each history short. Its workflow ID carries the stage number, and the stage version on every write rejects a late result from an older stage.

The parent never has two children open. It stops a child by cancellation request, so the child withdraws its open tasks and writes its last row, and waits for it to close before starting the next. It continues as new only when no child is open. It completes when the claim closes; a later reopen starts a new run with the same workflow ID and continues the stage numbering.

PaymentWorkflow is abandoned, not cancelled, when STP closes, and reports its result to the parent by signal.

Claim stages

Every stage change increments the stage version in the projection table. Every writing activity checks it and refuses a write from an older stage; ClaimsPro needs no change. More re-triages than the configured limit (three by default) go to ESCALATION. A failed child or an unknown outcome goes to MANUAL.

5. Human decisions

The workflow that needs a decision creates an adjuster task in ClaimsPro with its workflow ID and a decision ID, and waits with a deadline. The service behind Kong sends the adjuster's answer as Update decide to that workflow ID, with the decision ID as the Update ID. The validator rejects the decision before it is recorded if the task is closed, the choice is not offered, the role or authority is missing, the requester is the approver, or a required reason is missing (close, deny, reject). A repeated decision ID returns the first result. At the deadline the task moves to the next escalation role. Open tasks are withdrawn when the claim moves on.

6. Payments

STP fixes the payment key when it requests the payment. Create looks up that key first, so a retry never pays twice. A cancel signal is honoured until the payment closes. The result goes to the parent and the projection table.

Event for a claim with no running workflowRecorded by the bridge for review; not started

The event bridge reads database change events over JDBC, keeps only allowlisted, non-personal fields, sends each claim's events in order, and advances its read position after Temporal accepts the signal. One signal per event, deduplicated by event ID; 100 to 150 events per claim is far below the 10,000-signal limit. Every wait for an external result also re-reads on a timer, so a lost event delays a claim but does not strand it.

9. Contracts

Java and Python are generated from the same Protocol Buffers files (ClaimStart, ClaimEvent, TrackRequest, TrackResult, Decision, PaymentRequest, PaymentResult, ProjectionEvent and the activity messages). Payloads use protobuf JSON. Field numbers are never reused, fields are only added, enum value 0 is UNSPECIFIED and an unknown value goes to a person. No personal data appears in a message, workflow ID or search attribute.

10. Running in production

AreaDesign
Catastrophe loadNamespace capacity sized from the catastrophe peak (500 actions per second by default). Workers scale per queue on schedule-to-start latency; the queue rate limit holds ClaimsPro at its agreed rate. Verified with the client's catastrophe load-test scripts.
IsolationSeparate task queues and worker deployments keep STP apart from TSA and IS load.
History sizeContinue-As-New well below the 10,240-event warning; hard limit 51,200 events or 50 MB.
Billing (actions)Workflow start 1; child workflow start 2; signal 1; Update 1, accepted or rejected; Query 1; search attribute upsert 1; activity start or retry 1; timer 1; history export 1 per closed workflow. Measured: about 67 actions for a straight-through claim, 50 of them activities.
VersioningClaimLifecycleWorkflow on Auto-Upgrade with patching, since it lives for the whole claim; tracks and payment Pinned, and each old pinned version kept until its last workflow closes. New versions ramped; recorded histories replayed in CI before release.
RecoveryA Temporal Cloud namespace is replicated across three availability zones. Multi-region replication is an option (recovery point under one minute, recovery time about 20 minutes); history export does not fail over with it. Choice depends on the recovery targets.
SecuritymTLS and PrivateLink; one payload codec for Java and Python, failure messages included; codec server for authorised UI users. Search attributes and workflow IDs are not encrypted by the codec, so they hold IDs only. Keys rotate without making old histories unreadable; a worker with mTLS and no payload key refuses to start.
TestingTime-skipping tests for races among signals, timers, activity completion, cancellation and Continue-As-New; replay tests on every release.
ObservabilityELK logs carry claim, workflow and run IDs; LAMP for AI agents; Temporal Cloud and SDK metrics (Micrometer in Java) to dashboards. Search attributes ClaimId, Stage, Track, OpenDecision. Alerts: workflow task failures, queue latency, overdue decisions, steps past their retry window, export or archive failure.

12. Answers to the questions in the design document and the kickoff call

QuestionAnswer in this approach
One parent coordinating TSA, IS, STP children? Where is the boundary?Yes. The parent owns the stage, routing and cross-track rules only; each track owns its steps and returns an outcome. Children never call each other.
New child per track visit, or reuse one?New child per visit; its workflow ID carries the stage number, so histories stay short and versioning stays per visit.
Stage versions and lease tokens to reject stale results?Stage version on every write, checked against the projection table; a late write from an older stage is refused. No separate lease token.
Complete at close, or stay open for a reopen window?Complete at close. A reopen starts a new run with the same workflow ID (Signal-With-Start) and continues the stage numbering. A reopen that arrives while the run is closing is handled in that run.
Workflow ID reuse, retention, Signal-With-Start issuesOnly created and reopened events may start a run; a late created event for a closed claim ends at once. Retention starts at close; open claims are never deleted.
When to Continue-As-NewBetween stages, with no child open, when Temporal suggests it or above 5,000 events (warning at 10,240).
Projection table for years? Wait for each write?Yes, as the business record. Each row is written by an awaited, idempotent activity keyed claimId:stageVersion:step, so a step never moves on without its row.
Event history, Archival, audit logs, operational logs, projection: who keeps what?Section 8: history in Temporal then S3 by export; business history in the projection table then S3; logs in ELK; audit logs for namespace administration only.
Recovery if a row is missing after history expiresPrevented: rows are awaited and the record is verified complete before the claim workflow completes; the nightly check copies any history missing from S3 while it is still retained.
Bridge to parent to child, or directly to children?Bridge to parent; the parent forwards to the active child, holds events while no child runs, and every child re-reads ClaimsPro when it starts.
100 to 150 events per claim: signal per event or coalesce?Signal per event, deduplicated by event ID; far below the 10,000-signal limit. Each forward costs one action.
Human approval: Update or Signal? Parent or child?Update with a validator, on the workflow that waits for the decision; rejected decisions never enter history; the decision ID is the Update ID.
JSON Schema or Protocol Buffers? Schema version? Compatibility?Protocol Buffers, one definition for Java and Python. Fields only added, numbers never reused; unknown fields and enum values are read by both languages, and an unknown outcome goes to a person. Golden payloads are tested in both languages.
Condition change during an in-flight activityThe step in progress finishes; the stage version refuses any late write; a material change sends the claim to triage. A payment is never interrupted.
YAML/JSON flow definitionSTP flows from the variations tool: registered steps only, version and content hash recorded per claim. Payment authority has a ceiling in code that configuration cannot raise.
Auto-Upgrade parent, Pinned children? How long do old versions run?Yes. An old Pinned build runs until its last workflow closes. Every parent change passes replay of recorded histories.
Pass references or data to activities?References. Activities read current data when they run, so a retry a day later uses the latest data.

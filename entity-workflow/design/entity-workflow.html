Claims Orchestration on Temporal

Entity Workflow: one workflow per claim

1. Summary

Each claim is one long-running ClaimWorkflow: the standard Temporal entity-workflow pattern, one workflow per business entity for its whole life. Triage, investigation and STP are modules inside it, not separate workflows. Their work runs as activities on each track's own task queue and worker deployment: the Python team's AI and triage-rule activities on claims-tsa and claims-is, the Java STP activities on claims-stp, every ClaimsPro call on the rate-limited claimspro-activities queue. Events and every human decision arrive at the same workflow ID, claim:{claimId}. Payment runs in a region of the workflow that is never cancelled. Application data, S3, contracts and security are the same production baseline as Parent–Child Orchestration.

2. Why one workflow

Is a child workflow needed at each stage? Temporal's guidance is that child workflows are not a way to organise code; they are justified by a separate service or worker fleet that owns the workflow, a need to partition a very large history, or a one-to-one mapping to a separate resource. In this claims platform the tracks need separate workers (Python AI, Java STP) and separate deployments, which activities on their own task queues already give. The orchestration itself (stage, events, decisions, re-triage) is one coherent state machine for one claim, so it lives in one workflow.

PropertyWhat one workflow gives
One history per claimEverything that happened to a claim is in one execution (and its Continue-As-New chain)
One front doorEvents, decisions and queries all go to claim:{claimId}; nothing is forwarded or relayed
One place for cross-track rulesRe-triage limits, material change, stage version, payment authority live together
Fewer actionsNo child workflow starts (two actions each) and no forwarded signals
Independent deployment where it mattersActivity workers (Python AI, Java STP) deploy without workflow versioning concerns, as long as the activity contract holds

4. Inside the claim workflow

ModuleResponsibility
Stage machineThe claim's stage and stage version; routing between stages; re-triage limit; Continue-As-New between stages
Triage moduleRead claim, AI risk, triage rules, triage review when confidence is low; returns a route
Investigation moduleAI coverage analysis; waits for documents or an IS reviewer; returns to triage
STP moduleRuns the claim's flow definition: stages in order, steps of a stage in parallel; vendor dispatch, appraisal, estimate, reviews
Payment regionApproval above authority, create (payment key looked up first), close; run outside every cancellation scope
Decision deskEvery human decision: task in ClaimsPro, deadline, escalation, validated Update

Claim stages

Every stage change increments the stage version in the projection table; writes from an older stage are refused. The workflow completes when the claim closes; a reopen later starts a new run with the same workflow ID and continues the stage numbering. It continues as new between stages when the history is large, carrying its state, so one claim's history never approaches Temporal's limits.

A claim change during STP

Events are deduplicated and handled where they are needed, in the same workflow. On a claim change the workflow re-reads ClaimsPro and applies the material-change rule. A material change cancels the running STP stage at once (its activities are cancelled) and moves the claim to triage; the payment region is never cancelled and finishes first. Once money has moved, the change is recorded and STP closes the claim; a reopen brings it to an adjuster.

5. Human decisions

Every decision follows one lifecycle in the workflow: adjuster task created in ClaimsPro with the claim ID and decision ID; deadline timer; escalation through the roles in the authority matrix; the adjuster's decision sent by the service behind Kong as Update decide to claim:{claimId}, decision ID as Update ID; validation before anything is recorded (task open, choice offered, role, authority, requester is not the approver, reason where required); task closed, row recorded; open tasks withdrawn when the claim moves on.

6. Data outside Temporal and S3

Option for S3Where it appliesUse here
Temporal Archival (S3 archiver)Self-hosted Temporal only; experimental; not supported in DockerNot available on Temporal Cloud
Temporal Cloud Workflow History ExportEvery closed history to the client's S3 bucket hourly, protobuf, at least once; IAM role and KMS keyUsed: the developer record
Projection archiveNightly workflow: business rows of claims whose every run has closed go to S3, verified, then exactly those rows deletedUsed: the business record

As in Parent–Child Orchestration: Temporal holds IDs, stage and timers; ClaimsPro keeps claim data; the projection table keeps business history, written before the workflow moves on; Temporal Cloud has no Archival, so its Workflow History Export (hourly, protobuf, at least once) is the developer record in S3, with a nightly check that copies any missing history while it is still retained; the projection table is archived nightly to S3, verified before deletion. One claim, one workflow ID: the business row and the exported history join on it directly.

7. What we give to Temporal

Temporal Cloud runs the orchestration only. It receives IDs, stage, timers, decisions and encrypted payloads; claim data stays in ClaimsPro and business history in the projection table. This is the complete list of what is set up in Temporal Cloud for each environment; everything else runs in the client's AWS account.

10. Pros and cons

ProsCons and how they are handled
Simplest model: one claim, one workflow, one ID for everythingOne workflow type carries all tracks: kept in modules, reviewed and replay-tested as one
No event forwarding or decision relay; nothing to keep in sync between workflowsPython teams write activities, not workflows: their AI logic is the activity anyway
Fewest actions and executions per claimHistory grows with every track: Continue-As-New between stages
Activity workers deploy freelyEvery workflow change must be patched, as the claim workflow lives for the whole claim
Payment and re-triage rules in one placeA workflow defect stops the whole claim, not one track: replay tests and ramped rollout
